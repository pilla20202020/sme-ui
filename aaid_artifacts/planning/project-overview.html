1.

What This System Does

uw-ui is a React + TypeScript single-page application for individual health insurance enrollment and underwriting. Three user populations use it: members/applicants completing enrollment and plan-selection via emailed links, agents/brokers managing enrollments on behalf of clients, and admin/underwriter/back-office staff reviewing, approving, and tracking cases through an SSO-gated dashboard. It renders UI and drives workflows over the uw-backend NestJS API — it holds no database and makes no authorization decisions of its own.

This is a thin, presentation-only client
No persistent PII in the browser, no direct calls to SSO/document-storage/notification/e-signature providers (all backend-mediated), and no server runtime in production — static build, CDN-served.

Key Design Decisions

These summarize the ADRs in architecture.md — read that document for full context and consequences.

Architecture Decision Records — Summary
DecisionWhat / Why
ADR-001
Thin-client SPA		No business logic or auth decisions client-side; every check is re-verified by uw-backend.
ADR-002
Domain-driven folders		src/domains/<domain>/{api,hooks,types,components,pages} — chosen over technical-layer folders so each workflow can evolve independently.
ADR-003
TanStack Query owns server state		Caching, dedup, and invalidation for anything from the backend — never duplicated into Zustand.
ADR-004
Zustand is client-UI-state only		Drawer/modal state, in-progress form position — nothing that originated from the backend.
ADR-005
Dual auth model		Staff use SSO → session cookie; members use a link token + OTP. Architecturally separate paths inside one SPA, not two apps.
ADR-006
UI-level RBAC is UX, not security		hasRole/hasPermission hide/show UI; the backend independently authorizes every write.
ADR-007
No sensitive data in persistent storage		Cookie-based session preferred over localStorage; one legacy sessionStorage token is a known, scoped exception (see §6).
ADR-008
Static build + CDN delivery		vite build output served from a CDN; per-environment config baked in at build time via VITE_* vars.
ADR-009
Client-side validation is a first pass		Zod schemas give fast form feedback; backend validation errors are still handled and surfaced distinctly.

How the Pieces Connect

mermaid — system flow 
graph TD
    Users[Member / Agent / Admin] -->|HTTPS| CDN[CDN — static bundle]
    CDN --> App["App.tsx — provider shell"]
    App --> QC[QueryClientProvider]
    App --> Theme[ThemeProvider]
    App --> Auth[AuthProvider + AuthGate]
    Auth --> Router[BrowserRouter + AppRouter]
    Router --> Domains["src/domains/* — auth, dashboard, enrollments,
      activity, member-portal, member-questions, otp, plan-selection"]
    Domains --> Hooks[TanStack Query hooks]
    Domains --> Stores[Zustand stores — UI-only state]
    Hooks -->|fetch, credentials: include| Backend[uw-backend REST API]
    Domains --> Shared[shared/ — components, hooks, utils]

Every request enters through the CDN as a static asset; there's no server-side routing. App.tsx nests providers in a specific order — LoadingProvider → QueryClientProvider → ThemeProvider → AuthProvider → BrowserRouter → AuthGate → AppRouter. AuthGate is the traffic cop: it lets /member-portal/* routes through unconditionally (member link-token flow) and blocks everything else until AuthContext resolves a staff session (SSO redirect or cookie resumption).

Once past the gate, AppRouter renders a domain's page, which composes TanStack Query hooks (server state) and Zustand stores (client-only UI state) from that domain's api/, hooks/, and types/ files. Cross-cutting UI primitives come from shared/, which depends on nothing in domains/ or app/ — that dependency direction is load-bearing.

5.

Critical Paths

5.1

Staff Login (SSO)

1. Gate checkUnauthenticated staff user hits any non-/member-portal route → AuthGate sees status: 'checking', then 'unauthenticated'.
2. Redirect to IdPAuthProvider's checkAuth() effect finds no session cookie and no ?token= → redirectToSsoLogin() sends the browser to the IdP.
3. IdP redirect backIdP redirects with a token in the URL (getTokenFromUrl()).
4. Session exchangecreateSession(token) → POST /auth/session exchanges it for an HTTP-only session cookie; the raw token is also kept in sessionStorage['uw_access_token'] for a small set of legacy Bearer endpoints, then stripped from the URL.
5. AuthenticatedAuthContext sets user, roles, permissions, status: 'authenticated' → AuthGate renders AppRouter.
6. Reload / resumeOn reload, no URL token is found → fetchAuthMe() (GET /auth/me) resumes the session from the cookie.
5.2

Admin Approves an Enrollment

1. List loadsUnderwriter opens /enrollments; EnrollmentsPage.tsx renders via useEnrollmentsQuery(filters) → GET /enrollments?....
2. Approve actionUnderwriter opens a case in EnrollmentDrawer.tsx, clicks Approve → useEnrollmentMutations().approve.mutate({ id }).
3. Backend re-checksenrollmentApi.ts calls POST /enrollments/approve with the session cookie; uw-backend re-checks the enrollments:approve permission and writes the status + audit row.
4. Cache invalidationOn success, the mutation invalidates the ['enrollments'] query key; TanStack Query refetches the list and the UI reflects the new status. No optimistic update is applied for this compliance-relevant transition.
5.3

Member Completes the Medical Questionnaire

1. Link entryMember clicks an emailed link with a token → lands on a member-questions/member-portal route, bypassing AuthGate's SSO check entirely.
2. Token validationuseMemberAccess(token) → GET /member/questions/access?token= validates the link and returns a MemberAccessGrant.
3. OTP verificationMember requests and enters an OTP (shared otp domain) → send-otp / verify-otp → establishes a short-lived MemberSession held in memory, not localStorage.
4. SubmissionMember submits answers → useSubmitAnswers() → POST /member/questions/answers. No long-lived client cache is kept once submitted.

6.

Non-Obvious Things

Things that will surprise a new engineer — worth reading before your first PR.

  • Two authentication systems coexist in one SPA. SSO/cookie auth for staff and link+OTP for members are not interchangeable, and AuthGate special-cases the /member-portal prefix. A new member-facing route outside that prefix will silently be forced through the SSO gate.
  • A legacy Bearer token lives in sessionStorage, against the project's general no-persistent-sensitive-storage posture. Kept only because a handful of endpoints (email content/forward) still expect it — don't extend this pattern for new endpoints.
  • VITE_API_BASE_URL_V1 is missing from .env.example despite being required by almost every API module. Most modules throw at import time if it's unset — copying the example file verbatim produces a hard failure.
  • VITE_ADMIN_URL is set in .env but unreferenced in src/. Either dead configuration or a not-yet-implemented redirect — don't assume it's wired up.
  • The checked-in README.md describes a folder structure that no longer exists (components/, features/, context/, data/ instead of the current domains/, app/, stores/, shared/). Trust src/ and this document instead.
  • Server state and client state are split across two libraries by convention only. Nothing technically prevents caching server data in a Zustand store — watch for it in review.
  • UI-level hasPermission()/hasRole() checks are UX only. A missing permission check on a new backend endpoint is a real security gap even if the corresponding UI button is correctly hidden.
  • Enrollment approval never applies an optimistic UI update — the UI waits for a fresh refetch after a successful mutation. This is intentional for a compliance-relevant state transition, not an oversight.

Onboarding Checklist

Ordered — do these in your first week, in this order.

  • 1. Read this document, then architecture.md in full (ADRs + Design Pattern Guide + Component Breakdown).
  • 2. Skim arch-views.md for the System Map and Data Flow diagrams — they show the request lifecycle visually.
  • 3. Copy .env.example to .env, then also add VITE_API_BASE_URL_V1 pointing at your local/QA uw-backend — it's required but not in the example file (see §6).
  • 4. Run npm install && npm run dev, confirm the app loads at http://localhost:5173 and that staff SSO login round-trips against your configured VITE_SSO_* values.
  • 5. Walk through §5's three critical paths in the running app: staff login, approving a test enrollment, and (if you have a test link) the member questionnaire flow.
  • 6. Read one full domain end-to-end as a template — src/domains/enrollments/ is the most complete example of the api/ → hooks/ → components/ → pages/ layering described in §4.
  • 7. Before your first PR, read the Design Pattern Guide's "Anti-patterns to avoid" table in architecture.md — most review feedback for new contributors traces back to one of those five patterns.
